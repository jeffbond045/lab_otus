# Эксперименты, исправления и ограничения

## 1. Пересекающиеся IPv4-агрегаты → blackhole

Изначально R16/R17 анонсировали в R18 один и тот же `10.20.200.0/28`, и R18 установил два равных пути (ECMP). На каждом из суммирующих маршрутизаторов появилась summary-запись на Null0. Если конкретная подсеть назначения находилась за другим маршрутизатором, отсутствие более специфичного маршрута позволяло сбросить пакет через Null0. Это **не** значит, что ECMP сам по себе ошибочен: проблема состояла в содержимом общих агрегатов и реальной таблице маршрутов.

Исправление: переназначили P2P так, чтобы R17 использовал `10.20.200.0/29`, R16 — `10.20.200.8/29`. IPv4 Loopback разделили на `10.20.255.8/31` и `10.20.255.16/29`. R18 Loopback0 перенесли на `10.20.255.24/32`.

## 2. Default summary и Null0

На R16 к R32 настроены `summary-address 0.0.0.0 0.0.0.0` и `summary-address ::/0`. На R32 видны только эти default-маршруты из EIGRP.

В опыте с IPv4 R18 создали Loopback18 `172.16.255.18/32`, не объявленный в EIGRP. При наличии на R16 статического default к R18 (`AD 1`) R32 мог достигать адреса. После удаления реального default пакеты попадали под менее предпочтительную summary-запись default на Null0 и пинг прекращался. Это демонстрирует, что анонс default на R32 **не создаёт** реальный транзитный путь автоматически.

Аналогичный опыт проведён с IPv6 Loopback6 R18 `FD41:D52F:5041:5002::33/128`. Для подавления маршрута /128 на R16 применили входящий prefix-list. При наличии реального IPv6 static default трафик проходил; без него — нет. В последнем показанном конфиге R16 фильтр ещё присутствовал. Диагностический Loopback6 оставлен намеренно; Loopback18 также виден в RIB R18.

## 3. Потерянный IPv4 Loopback R32

После изменения адреса на R32 на `10.20.255.19/32` старое точное правило `network ... 0.0.0.0` не включало интерфейс в EIGRP. На R16 первоначально не было конкретного маршрута /32, и его покрывал агрегат `10.20.255.16/29 → Null0`. Правило исправили на `network 10.20.255.19 0.0.0.0`. Затем R16 получил `D 10.20.255.19/32 via 10.20.200.73` — конкретный маршрут предпочтительнее /29 по longest prefix match.

## 4. Явные ограничения готового состояния

- Требование «R16–R17 анонсируют только суммарные префиксы» **не исполнено буквально**: R18 по-прежнему получает `10.20.200.72/30` от R16 и отдельные IPv6 Loopback `/128`. В отчёте это не скрывается.
- IPv6 Loopback не суммировали, чтобы не переадресовывать существующие адреса и не создавать пересекающиеся агрегаты.
- SW9 на момент ICMP-проверки выключен. Доступность SW9 и нижних VPC не подтверждена, конфигурации SW9/SW10 позднее извлечены из EVE-NG и показывают отсутствие EIGRP и IPv6, поэтому интеграция SW не завершена.
- Полный running-config R18 не предоставлялся; подтверждены только его RIB/соседи/топология и отдельные интерфейсы по результатам.
- Статические default на R16 направлены на R18; доступность сетей за R18 отдельно не проверена.
- В последнем подтверждённом конфиге R16 остаётся входящий IPv6 prefix-list `LOOP_6_deny_test`. Его нельзя описывать как удалённый без повторного вывода.
- Оба R16/R17 используют `network 10.0.0.0` для IPv4 — широкое правило включения интерфейсов; в текущей лаборатории работает, в production лучше использоваь точные маски.
